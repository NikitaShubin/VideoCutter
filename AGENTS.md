# Правила разработки VideoCutter (обязательны для любых изменений)

## TDD — единственный порядок работы

1. **Критерии приёмки списком** — что должно наблюдаться снаружи.
2. **Падающие тесты** — фиксируют критерии до кода.
3. **Минимальный код** до зелени, затем рефакторинг.
4. Готовность = весь сьют зелёный + гейт покрытия 99% в CI.

Для багов — сначала падающий регрессионный тест, воспроизводящий баг,
потом фикс (пример: чужие префиксы `task_N/` — 3 падения без фикса).

## Каким должен быть тест

- **Один тест — одно наблюдаемое поведение** (статус, тело ответа, файлы
  на диске, метаданные). Сложность — в данных сценария и фикстурах,
  никогда в теле теста: без ветвлений и «проверок всего сразу».
- **Тесты фиксируют контракт, не реализацию**: вызовы приватных функций,
  структура внутренних словарей, порядок вызовов моков — не предмет
  ассертов. Тест, падающий от чистого рефакторинга без смены поведения, —
  сигнал переписать тест, а не код.
- Существующие тесты не удаляются и не упрощаются ради концепции;
  удаление — только поштучно с согласия владельца.
- Отладочные скрипты и reproduce-куски в репозиторий не коммитятся:
  либо дистиллируются в один регрессионный тест, либо удаляются.

## Приёмы сюиты (переиспользовать, не изобретать)

- Базы: `WorkspaceApiTestBase` (фикстура workspace+видео+tsv),
  `ProjectTestBase`, хелперы `BackupArchiveMixin`, `_wait_ready`.
- 5xx в тестах: `logging.disable(logging.CRITICAL)` вокруг запроса
  (иначе harness падает на логгинге), затем `logging.disable(NOTSET)`.
- Стриминг-ответы: `b"".join(resp.streaming_content)` + `resp.close()`.
- Параллельный прогон: `DJANGO_DEBUG=0 ... test --parallel 4`
  (воркеры forkserver переимпортируют settings с DEBUG=1 — иначе тесты
  с пробрасываемыми исключениями падают на рендере debug-500).
- Замер покрытия — только отдельным последовательным прогоном
  (coverage несовместим с `--parallel`): `coverage run ... manage.py test`,
  гейт `--fail-under=99`.
