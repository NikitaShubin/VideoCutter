# Бенчмарк воспроизведения: таблица метрик по видео

## Методика

- Замер — `tools/bench_playback.py` с хоста через HTTP API: для каждого
  видео запрашиваются **все** кадры подряд вперёд (`0..N-1`) и назад
  (`N-1..0`), каждый кадр — отдельный запрос, `quality=75`, `scale=1.0`
  (ресайз не применяется), пропуски запрещены. 404 копятся, не прерывают.
- Перед каждым видео контейнер рестартуется (холодный кэш).
- Метрика видео: `M = (T_fwd + T_bwd) / 2 / (W·H·N)` (сек/пиксель),
  плюс «кадр/с» = `N / ((T_fwd + T_bwd) / 2)`.
- `N` берётся из `total_frames` пары (превью). Для задачи `6` оба вида
  (`original`, `visualization`) меряются на `N` превью: source.mp4 реально
  содержит 807 кадров, запрашиваются первые `N` (ограничение скрипта,
  одинаково для всех строк таблицы).
- Эталон — `tools/bench_engine_reference.py` внутри контейнера:
  последовательный `cv2.VideoCapture.read()` (эмуляция десктопного
  PyVideoCutter). PyAV-часть падает на битом `preview.avi`
  (`InvalidDataError`) — известное свойство файла, не движка.

## Выводы

1. O2 закрыл главный провал: реверс длинных GOP идёт из памяти
   (сотни кадр/с вместо ~12).
2. Visible-индекс убрал 404 preview.avi полностью: было 72×404 (~57s
   штрафов), стало 0; visualization 22 → 90 кадр/с. Остаток времени —
   фиксированная цена per-GOP (open/seek/декод 37 мелких групп).
3. `test` (32×32) ограничен per-request overhead HTTP (~10–14 мс) —
   движком не лечится, видео игрушечное.
4. Разброс bwd crowd/source между прогонами (0.35→0.96s, 0.41→0.88s) —
   шум loopback-пропускной/состояния машины, порядок величин тот же.
   При сомнениях — перегнать конкретную строку отдельно.
5. O4 (направленный префетч) убрал холодные старты групп на реверсе
   мелких GOP: preview-bwd 10.63s → 4.46s (×2.4); остаток — пол
   per-frame JPEG+HTTP. Регрессий по остальным строкам нет.
6. Сырые логи прогонов: `/tmp/opencode/{baseline_current,reference_cv2,
   o2_jpeg_cache,ref_current,playback_current,playback_dirpref}.txt`
   (эфемерно, в репо не входят).
