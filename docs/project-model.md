# Модель проекта VC: `project.json`

Проект — отдельная сущность (как в CVAT): группировка задач и контекст
для будущей модели визуализации/AL. Задачи независимы: живут в своих
папках и могут быть standalone (без проекта) или входить в один проект.

## Почему файлы, а не БД

Весь VC stateless (см. `task-model.md`): проекты лягут в ту же схему —
чтение per-request, запись атомарно (tmp+rename), памяти в ядре ноль.

```
workspaces/projects/<pid>/project.json   — сам проект (реестр)
workspaces/<task>/task.json              — указатель project_id (членство)
workspaces/.projects_migrated            — маркер разовой миграции
```

**Членство хранится на задаче** (`project_id: string | null`), не
списком участников на проекте — ровно как `Task.project_id` в CVAT.
Следствия:

- состав проекта резолвится сканом указателей — двух источников правды
  нет, расхождение исключено структурно;
- «задача в двух проектах» невозможна по построению;
- удаление задачи не оставляет битых ссылок (указатель-то на ней самой);
- висячий указатель (проект удалён вручную) резолвится в standalone.

## Формат `project.json` v1

```json
{
  "id": "string | null",
  "name": "Отображаемое имя",
  "created_at": "iso8601 | null",
  "model": { "id": null, "kind": "", "params": {} }
}
```

Правила — как у `task.json`:

- читатель игнорирует неизвестные ключи, писатель сохраняет их
  (расширяемость без миграций: `labels`, `al_policy` и пр. лягут сюда);
- битый JSON = дефолты + warning в лог (реестр не роняем);
- `id` = имя папки, неизменяем (как у задач); `name` свободно правится;
- `model` — **заглушка-точка расширения**: только хранение, путей
  исполнения нет; сюда же встанет конфиг будущей модели.

## Миграция в `default`

Первый скан существующей установки (до появления маркера
`.projects_migrated`) создаёт проект `default` и привязывает все задачи
без проекта. Дальше маркер запрещает повтор: standalone после этого —
уже явное решение пользователя (detach). Запись членства не двигает
mtime папки задачи — сортировка «Недавние» не прыгает от миграции.

Новые задачи: пока `default` существует — рождаются в нём; после его
удаления — standalone (и попадают в проект только вручную).

## Привязка: `can_attach`

Attach/detach идут через хук `project_meta.can_attach(task, project)` —
по образцу CVAT `TaskWriteSerializer.update_project`. Сейчас: проверка
существования обеих сущностей (и зарезервированного имени `projects`).
Точка для будущих ограничений совместимости, когда появятся метки и
модель: метки задачи ⊆ меток проекта, совместимость семейства медиа
(наш аналог `dimension`/media type) и т.п.

Свобода привязки сейчас полная (как через cvat-sdk): перевеска в другой
проект — одной операцией, отвязка — в standalone.

## API (v1)

| Метод | Путь | Смысл |
|---|---|---|
| GET | `/api/v1/projects/` | список + `task_count` |
| POST | `/api/v1/projects/` | создать `{"name"}` (id = имя) |
| GET/PUT | `/api/v1/projects/<pid>/` | чтение; правка `name`/`model` |
| DELETE | `/api/v1/projects/<pid>/?with_tasks=…` | `cascade` (дефолт, как в CVAT) / `keep` / `move&to=<pid>` |
| POST | `/api/v1/projects/<pid>/tasks/` | attach `{"task_id"}` |
| DELETE | `/api/v1/projects/<pid>/tasks/<tid>/` | detach |

Фильтр задач: `GET /api/v1/workspaces/?project=<pid>` (`none` —
standalone; без параметра — все).

## Соответствие CVAT

| CVAT | VC |
|---|---|
| Project (отдельная сущность) | `workspaces/projects/<pid>/project.json` |
| `task.project_id` (FK, nullable) | `task.json::project_id` (nullable) |
| labels проекта/задачи, subset при attach | не копируем (нет меток); хук `can_attach` — под них |
| dimensions/media type проверка при attach | точка расширения: семейство кодека/разрешение/fps |
| удаление проекта = каскад | то же (`with_tasks=cascade` дефолт) |
| backup проекта = project.json + вкладыш задач | бэкап/экспорт — отдельным этапом |
| AI model проекта | `model`-заглушка (хранение без исполнения) |
