# Фоновые операции: очередь, статусы, история

Единая система длительной работы: экспорт нарезок, бэкапы и восстановление,
импорт/экспорт разметки, индексация и валидация. Документ фиксирует границу
ядра и обвязки, модель данных, планировщик, API, UI и контракт с VDO.

## Статус реализации

Работает локальный контур: записи операций на диске, планировщик с
полосами, отмена/повтор/рестарт, API `/api/v1/jobs*`, журнал активности
(JSONL), экран `/operations` и все тяжёлые типы: экспорт нарезок, бэкапы
задач/проектов, экспорт и импорт разметки, импорт бэкапов, индексация и
валидация. Архивы бэкапов и разметки кэшируются с TTL. Старые
`/pairs/<id>/export*` и `/backups/*` пока работают на прежнем пути; их
перевод в тонкие алиасы — следующий шаг миграции.

Ещё не реализованы: чтение журнала через API, внешние зависимости и
колбэки VDO. Ниже они помечены как проектируемые — это не текущее
поведение.

## 1. Термины

**Операция (job)** — единица фоновой работы с идентификатором, владельцем,
статусом, прогрессом и результатом. Не путать с CVAT job (сегмент задачи).

**Очередь** — планировщик операций внутри процесса VC. В автономном режиме
очередь принадлежит VC. В VDO межсервисная очередь принадлежит VDO; VC даёт
исполнителей и декларации типов (раздел 10).

**Полоса (lane)** — очередь однородных операций с собственной ёмкостью:
`export` (процессор), `archive` (диск), `import` (диск + процессор),
`system` (индексация/валидация). Разнородные операции в одной полосе не
смешиваются: у них разные лимиты и приоритеты.

**Владелец (owner)** — пользователь, запустивший операцию. В автономном
режиме — `local`; в VDO — идентификатор пользователя из доверенного
заголовка прокси.

**Отпечаток (fingerprint)** — версия состояния объекта: идентичность видео
(`size+mtime`), границы фрагментов, mtime паспорта. Всё выводится из файлов;
отдельного реестра версий нет.

## 2. Граница ядра и обвязки

- `videocutter/core` не знает про операции, очередь, статусы и HTTP. Ядро
  умеет резать, проверять и считать — по запросу.
- `backend/vc_jobs` — обвязка: записи операций на диске, планировщик,
  HTTP API, журнал активности. Импортирует ядро и workspace, не наоборот.
- Исполнитель типа операции — тонкая функция обвязки. Она получает
  `JobContext` (прогресс, отмена) и вызывает ядро/адаптеры.
- UI — часть доменной модели: правила отображения статусов и действий живут
  в одном месте для автономного VC и VDO. Данные UI получает через API.

Правило: новый тип операции добавляется регистрацией `JobType` и
исполнителем. Очередь, API и UI не меняются.

## 3. Хранение состояния

Корень состояния — `VC_STATE_ROOT` (по умолчанию `<VC_WORKSPACE_ROOT>/.vc-state`).
Сканер workspace пропускает каталоги с точкой, поэтому состояние не
воспринимается как задача.

```
.vc-state/
├── jobs/<uuid>.json          # запись операции, атомарная замена
├── activity/YYYY-MM-DD.jsonl # журнал активности, суточные файлы
├── archives/<type>/<key>.zip # кэш бэкапов и разметки
├── archives/<type>/<key>.json# метаданные кэша: TTL, цель, имя файла
├── uploads/<id>.zip          # загруженные архивы для импорта
└── locks/                    # межпроцессные блокировки (позже)
```

Запись операции — **факт о задаче**, а не кэш: переживает рестарт. Это
явное исключение из правила «память не переживает файл» (см. AGENTS.md,
README). Активная очередь — память процесса; после рестарта она
восстанавливается из записей.

Запись пишется атомарно: временный файл в том же каталоге, `flush`+`fsync`,
`os.replace`, режим `0644`. Прогресс обновляется не чаще раза в секунду,
чтобы не изнашивать диск. Битая запись пропускается с предупреждением в
журнал, сервис не падает.

### Схема записи (v1)

```json
{
  "v": 1,
  "id": "0f0c…",
  "type": "export.fragments",
  "lane": "export",
  "status": "queued",
  "dedupe_key": "export.fragments:task:camera_8_13:owner:local",
  "owner": "local",
  "target": {"kind": "task", "id": "camera_8_13", "project_id": null},
  "params": {"format": "mp4"},
  "priority": 0,
  "depends_on": [],
  "attempt": 1,
  "progress": {"current": 0, "total": 33, "unit": "fragment", "message": ""},
  "result": null,
  "error": null,
  "cancel_requested": false,
  "created_at": "2026-11-22T12:00:00+00:00",
  "started_at": null,
  "finished_at": null,
  "heartbeat_at": null,
  "retention": {"expires_at": null, "keep": true}
}
```

Статусы: `queued`, `running`, `done`, `error`, `cancelled`, `interrupted`.
`cancelling` — только вычисляемое состояние (`running` + `cancel_requested`),
на диск не пишется. Терминальные: `done`, `error`, `cancelled`, `interrupted`.

`interrupted` — операция была в работе и процесс завершился. Для
возобновляемых типов планировщик при старте переводит её обратно в `queued`
(новый `attempt`), для остальных оставляет как факт с просьбой запустить
заново.

## 4. Планировщик

Один планировщик, несколько полос. Ёмкости:

| Полоса | По умолчанию | Настройка |
|---|---|---|
| `export` | `max(1, min(4, ncpu // 4))` | `VC_EXPORT_WORKERS` |
| `archive` | 1 | `VC_ARCHIVE_WORKERS` |
| `import` | 1 | `VC_IMPORT_WORKERS` |
| `system` | 1 на HDD, иначе 2 | `VC_INDEX_BG_THREADS` |

Глобальный предел `VC_JOBS_MAX` (по умолчанию 4) не даёт полосам суммарно
забить машину. Внутри полосы — приоритет, затем FIFO по `created_at`:

- `0` — интерактивное действие пользователя (экспорт, бэкап, импорт);
- `10` — массовая операция пользователя;
- `100` — системная работа (индексация, валидация);
- `1` — предпосылка активной пользовательской операции (обгоняет чужую
  системную работу, но не другие действия пользователя).

Планировщик — демон-поток с условной переменной: `submit`, `cancel`,
завершение исполнителя и таймер будят его. Исполнители работают в отдельных
потоках. Ёмкость полосы занимается до старта потока, освобождается в
`finally`, после чего планировщик добирает очередь.

### Дедупликация

`dedupe_key = type + target + owner (+ вариант параметров)`. Повторный
активный запрос возвращает существующую операцию (`deduplicated: true`),
а не создаёт вторую. Разные владельцы могут параллельно работать с одним
объектом — у них разные ключи. Для системных операций владелец не входит в
ключ, вместо него — отпечаток состояния.

### Предпосылки и каскад

`JobType.prerequisites(spec)` возвращает список спецификаций, которые
должны завершиться до старта. Планировщик материализует их с тем же
отпечатком и приоритетом `1`, пропускает уже готовые и связывает
`depends_on`. Глубина каскада ограничена 4, цикл — ошибка.

Пример: экспорт требует свежую валидацию задачи; открытие неиндексированной
задачи запускает `system.index`, затем `system.validate`. Пользователь
видит «Подготовка» вместо молчаливого ожидания. Отмена предпосылки
переводит зависимые операции в `error` с кодом `prerequisite_cancelled`.
Провал — `prerequisite_failed`.

Прерывание из-за остановки сервиса — не провал: возобновляемая
предпосылка при рестарте встаёт обратно в очередь, зависимые остаются
`queued` и дожидаются её. Если тип не возобновляемый, зависимые получают
`prerequisite_failed`: ждать больше нечего. Задача, отменённая до
остановки, остаётся `cancelled` — ручная отмена не возобновляется.

### Отмена

Отмена кооперативная: исполнитель получает `ctx.cancelled()` и обязан
проверять его между шагами, а долгие подпроцессы (ffmpeg) убивать сразу.
`queued` отменяется мгновенно; `running` получает `cancel_requested`, API
показывает «Отмена…», затем статус `cancelled`. Ручная отмена не
возобновляется после рестарта никогда.

Системные операции отменяемы вручную. Если у них есть зависимые активные
операции, те завершаются ошибкой `prerequisite_cancelled`.

### Рестарт

При старте процесса:

1. `queued` — возвращаются в очередь на прежнее место по `created_at`.
2. `running` — `interrupted`; если тип возобновляемый и отмены не просили,
   запись переводится в `queued`, `attempt += 1`.
3. `cancelled` — не возобновляется.
4. `done`/`error` — остаются фактами.

Исполнители идемпотентны: пишут во временные файлы и публикуют атомарным
`rename`. Повторный запуск после обрыва безопасен.

## 5. Типы операций

| Тип | Полоса | Отмена | Рестарт | Результат | Хранение |
|---|---|---|---|---|---|
| `export.fragments` | export | да | да | файлы в `exports/` | постоянно |
| `backup.task` | archive | да | да | zip | TTL 7 дней |
| `backup.project` | archive | да | да | zip | TTL 7 дней |
| `annotations.export` | archive | да | да | zip | TTL 24 часа |
| `backup.import` | import | да | нет | новая задача/проект | — |
| `annotations.import` | import | да | нет | разметка | — |
| `system.index` | system | да | да | индекс кадров | производное |
| `system.validate` | system | да | да | отчёт валидации | производное |

TTL архивов повторяет CVAT: срок отсчитывается от последнего скачивания
(`mtime` обновляется при выдаче), чистка — раз в час. Нарезки фрагментов —
конечный продукт автономного режима и **не протухают**.

Повторный запрос бэкапа сверяет отпечаток: если архив с тем же отпечатком
уже есть и не истёк — отдаётся он, сборка не запускается. Иначе создаётся
новая операция (поведение CVAT). После пересборки архивов старой версии
для той же цели удаляются.

Импорт разделён на два шага: файл один раз загружается в
`uploads/<id>.zip` (`POST /jobs/uploads`, ответ `201` с `id`), затем
операция получает только идентификатор. Так повтор запроса не передаёт
гигабайты заново, а HTTP-соединение не держится на время распаковки.
`backup.import` принимает `on_conflict` (`error|rename|overwrite`) и
`project`; `annotations.import` — `upload_id` и `force`. Загруженные
архивы живут сутки (`VC_JOB_UPLOAD_RETENTION_DAYS`) и ограничены
`VC_JOB_UPLOAD_MAX_MB` (8192).

Перед экспортом планировщик материализует `system.validate`, а тот —
`system.index`. Ключ идемпотентности — отпечаток видео (`size+mtime`):
пока файлы не менялись, готовая проверка переиспользуется. Открытие
задачи ставит ту же проверку в очередь (приоритет системной работы);
успех снимает старую отметку о поломке, сбой записывает её в workspace
без перезапуска процесса.

## 6. API

Все пути — с `/api/v1` и без завершающего слэша (как остальной API).

| Метод | Путь | Ответ |
|---|---|---|
| POST | `/jobs` | `202` запись операции; при дедупликации — та же запись и `deduplicated: true` |
| GET | `/jobs` | `{jobs: [...], next: cursor}`; фильтры `type`, `status`, `owner`, `target`, `project_id`, `limit`, `cursor` |
| GET | `/jobs/<id>` | запись операции |
| POST | `/jobs/<id>/cancel` | `202` запись; `409` для терминальной |
| POST | `/jobs/<id>/retry` | `202` новая операция с тем же `params` и `attempt + 1` |
| GET | `/jobs/<id>/download` | файл/архив; `409` пока не готово, `410` если истёк |
| GET | `/jobs/summary` | счётчики по статусам для бейджа вкладки |
| GET | `/jobs/types` | манифест зарегистрированных типов |
| POST | `/jobs/uploads` | `201` `{id, name, size}`; файл для импорта в `uploads/` |

Тело `POST /jobs`:

```json
{"type": "export.fragments", "target": {"kind": "task", "id": "camera_8_13"},
 "params": {}, "priority": 0}
```

Владелец не приходит в теле: его определяет обвязка. Автономно — `local`;
в VDO — доверенные заголовки прокси `X-VC-User`, `X-VC-Roles` при
`VC_TRUST_PROXY=1`. Заголовки принимаются только от прокси и никогда не
используются для повышения прав внутри VC.

Видимость: автономно видны все операции; в VDO — свои, администратору —
все (как Requests в CVAT). Чужая операция не раскрывает параметры и пути.

Идемпотентность: `Idempotency-Key` (необязательный) добавляется к
`dedupe_key`; повтор с тем же ключом возвращает ту же операцию.

## 7. UI

Третья вкладка переключателя «Задачи / Проекты / Фоновые операции»,
маршрут `/operations`, бейдж с числом активных операций. Не скрытая панель
в шапке: это полноценный экран, как Requests в CVAT.

Карточка операции — одновременно кнопка и статус-бар:

- тип и объект со ссылкой (`/tasks/<id>`, `/projects/<id>`);
- владелец, время создания/завершения;
- прогресс `12 / 33` с `role="progressbar"`;
- действия: «Отменить», «Повторить», «Скачать», «Открыть задачу»;
- терминальные статусы — цвет и текст, без ложной активности.

Кнопки запуска в редакторе (экспорт, бэкап, импорт) после нажатия
превращаются в тот же статус-бар: прогресс, отмена, по завершении —
скачивание. Отдельного «списка очереди» в редакторе нет.

Опрос адаптивный: 2 с при активных операциях, 15 с в покое, пауза при
`document.hidden`, немедленное обновление при возврате на вкладку и после
действия. SSE/WebSocket — позже, когда появится межсервисная очередь.

## 8. Журнал активности

Лёгкий append-only JSONL, без БД и без обязательного Grafana:

```json
{"ts":"2026-11-22T12:00:00+00:00","actor":"local","action":"job.done",
 "target":{"kind":"task","id":"camera_8_13"},"project_id":null,
 "job_id":"0f0c…","summary":"Экспорт: 33 нарезки","link":"/tasks/camera_8_13"}
```

Пишут только обвязка и исполнители. События: `job.created`, `job.started`,
`job.done`, `job.failed`, `job.cancelled`, `job.retried`, `task.opened`,
`fragments.saved`, `backup.imported`, `annotations.imported`. Поля —
минимальные, без секретов и содержимого разметки.

Файлы суточные, хранение `VC_ACTIVITY_RETENTION_DAYS` (90 дней), чистка при
плановом тике. Чтение через API — проектируемое:
`GET /activity?from=&to=&project_id=&task_id=`. Grafana может читать те же
JSONL через сборщик, но зависимостью не является.

## 9. Права на файлы

Артефакты экспорта: каталог `0755`, файлы и sidecar `0644`, незавершённые
файлы `0600`. Предки workspace получают только проход `o+x` до
`VC_ACCESS_ANCHOR` (по умолчанию корень workspace). Режимы фиксированы:
чужие пользователи хоста обязаны читать готовые нарезки.

`ensure_access` после `chmod` проверяет фактический режим. Если файловая
система игнорирует права (NTFS/exFAT/CIFS с `fmask`), в журнал пишется
явное предупреждение, а диагностика доступна в `GET /api/v1/cache`.
Починка прав идемпотентна и запускается при старте, при экспорте и при
скачивании, а не только в момент создания файла.

## 10. Контракт с VDO

VDO забирает себе то, что по правилу границы принадлежит внешнему контуру:
пользователей, роли, доступ к файлам и межсервисную очередь. VC остаётся
исполнителем и хранилищем форматов.

Формальный интерфейс:

1. **Манифест типов.** `GET /api/v1/jobs/types` отдаёт JSON-описание:
   `key`, `lane`, `label`, `params_schema`, `result_kind`, `cancellable`,
   `resumable`, `retention_days`, `has_prerequisites`. VDO строит по нему
   формы и маршрутизацию, не копируя правила.
2. **Исполнитель как порт.** `JobType.executor(job, ctx)` не знает, кто его
   вызвал. Автономный VC запускает его локальным планировщиком; VDO может
   запускать тот же исполнитель своим воркером.
3. **Внешние зависимости.** `depends_on` — непрозрачные строки. Локальный
   планировщик считает внешнюю зависимость готовой только после
   `POST /jobs/<id>/deps` от доверенного контура (проектируемое). Так VDO
   связывает операции разных сервисов, не отдавая VC свою очередь.
4. **Локаторы, а не пути.** Вход и выход передаются как локаторы
   (`{"kind":"path"|"url", "value":...}`). Экспортёр пишет только в
   переданный каталог; выбор каталога — решение обвязки.
5. **Колбэки.** Необязательный `callback_url` + HMAC-подпись: VDO узнаёт о
   терминальном статусе без опроса (проектируемое). В автономном режиме
   выключено.
6. **Идемпотентность.** `Idempotency-Key` и `dedupe_key` позволяют VDO
   безопасно повторять запросы после сетевого сбоя.
7. **Идентичность.** VDO передаёт `X-VC-User`/`X-VC-Roles` через прокси;
   VC доверяет им только при `VC_TRUST_PROXY=1`. Автономный режим — `local`.

UI переиспользуется: экран `/operations` и статус-бары кнопок работают с
любым бэкендом, реализующим этот API. Пользователь переходит из VC в VDO
без смены привычек.

## 12. Критерии приёмки

- Операция переживает рестарт: `queued` и `running` продолжаются, ручная
  отмена — нет.
- Повторный запрос той же операции не создаёт дубль.
- Полосы не превышают ёмкость; глобальный предел соблюдается.
- Отмена `running` останавливает ffmpeg и не оставляет опубликованных
  файлов; частичные файлы удаляются.
- Прогресс и статус видны в API и UI без перезагрузки страницы.
- Готовый бэкап переиспользуется при совпадении отпечатка и протухает по
  TTL; нарезки не протухают.
- Журнал активности переживает рестарт и содержит ссылку на объект.
- Права: другой пользователь хоста читает нарезку; неисправимая ФС даёт
  предупреждение, а не тихий отказ.
